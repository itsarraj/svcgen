# svcgen

Generates a systemd `.service` unit file with defaults that actually
matter, and validates an existing one for the mistakes that actually
bite in practice. The "Dockerfile generator" idea (this workspace's
`dockergen`) for the bare-metal/VPS deploy case instead of containers.

## Installation

```sh
cargo install --path .
```

## Usage

```bash
svcgen generate --exec /usr/local/bin/myapp --description "My App" \
  --user myapp --workdir /opt/myapp --env "PORT=8080" --out myapp.service

svcgen validate myapp.service
```

`validate` exits `0` clean, `1` on warnings only, `2` if there's a real
error (missing `[Service]`, missing `ExecStart=`, or a relative
`ExecStart=` path — systemd doesn't search `$PATH`, that one silently
fails at runtime otherwise).

## Generated defaults, and why they're not just the bare minimum

- `Restart=on-failure` — a crashed service just staying down is the most
  common systemd deploy mistake there is.
- `NoNewPrivileges=true`, `ProtectSystem=strict`, `ProtectHome=true`,
  `ReadWritePaths=<workdir>` — real hardening that costs nothing for the
  overwhelming majority of services, generated by default rather than
  left as flags you have to remember to add.
- A real `User=` line when given, rather than silently defaulting to root
  the way an empty template would.

## Status: built, and cross-checked against the real systemd toolchain — which caught something this tool's own validator missed

- **18 unit tests** (`cargo test --lib`): generation (hardening
  directives present by default, a given `User=` included, `User=`
  entirely *absent* rather than blank when none given, environment
  variables each on their own line, all three required sections
  present); the INI-style parser (duplicate keys within a section all
  kept, not overwritten — real unit files legitimately repeat
  `ExecStartPre=`; comments and pre-section-header lines correctly
  ignored); and validation (a well-formed file has zero issues; missing
  `[Service]` is one clear fatal error, not a flood of confusing
  follow-on errors; a relative `ExecStart=` path specifically flagged,
  not lumped in with "missing").
- **Cross-checked against the real `systemd-analyze verify`, not just
  self-consistency**: generated a real unit file, ran it through
  `svcgen validate` (clean), then through the actual `systemd-analyze
  verify` this machine has installed. **It caught something `svcgen`'s
  own validator didn't**: `User=nobody` produced a real systemd warning
  (`Special user nobody configured, this is not safe!` — `nobody` is a
  shared, deliberately-non-isolated system account, and systemd
  recommends a dedicated per-service user or `DynamicUser=yes` instead).
  Not hidden — regenerated with a real dedicated username and confirmed
  `systemd-analyze verify` then passed with **zero** warnings, and the
  `nobody` gap is now a known, documented limitation (see below) instead
  of a silently-wrong "no issues found."
- **The negative validation path verified against a real deliberately
  broken file too**: `[Service]\nExecStart=myapp\n` (relative path, no
  `Restart=`, no `User=`, no `[Install]`) produced exactly the right one
  `ERROR` plus four `WARN` lines and exited `2`.

**Found via the systemd-analyze cross-check, not yet fixed**: `validate`
doesn't know that `User=nobody`/`User=daemon` (shared system accounts)
are themselves a real systemd-flagged anti-pattern, distinct from simply
missing a `User=` line entirely — real systemd domain knowledge this
tool's own rule set doesn't encode yet. `systemd-analyze verify` (present
on any real systemd machine) remains the authoritative check either way;
this is a fast pre-check, not a replacement for it.

**Not done / deliberately deferred**: socket-activated services
(`.socket` units), timer units (`.timer`, systemd's cron equivalent) —
this only generates/validates plain `.service` files.
